# Import: маппинг DOCX/PDF → markdown-gost MD

Документ описывает, что именно постпроцессор распознаёт в выводе pandoc и во
что сворачивает. Всё, что не описано здесь, остаётся «как есть» из pandoc.
Выходной синтаксис — только новый (см.
[skills/markdown-gost/syntax.md](../skills/markdown-gost/syntax.md));
legacy-директивы импорт не эмитит никогда.

PDF-вход проходит через unoserver-prepass: PDF → DOCX → дальше всё то же
(§5).

## 1. Pandoc-вызов

Перед pandoc исходный docx копируется и правится (`semantic_docx`):

- стиль «MD2GOST Structural Heading» переименовывается в `heading 1`,
  чтобы pandoc отдал `#`;
- безрамочные таблицы, у которых каждая «математическая» строка состоит из
  двух ячеек с коротким содержимым, разворачиваются в display-math
  параграфы (`m:oMathPara`) — pandoc дальше отдаёт их как `$$…$$`.

Сам вызов (вывод читается из stdout):

```
pandoc input.docx \
  --from=docx \
  --to=markdown_strict+pipe_tables+backtick_code_blocks+tex_math_dollars+raw_tex+bracketed_spans \
  --extract-media=<tmpdir>/media \
  --wrap=none
```

- `markdown_strict` — меньше pandoc-специфики; `pipe_tables` — GFM-таблицы;
  `tex_math_dollars` — `$…$`/`$$…$$`; `bracketed_spans` — `[text]{.underline}`;
  `--wrap=none` — надёжная regex-обработка; `--extract-media` — картинки в
  temp-папку.
- Бинарник и таймаут: `PANDOC_BINARY`, `PANDOC_TIMEOUT_SECONDS` (60 c).

Порядок постпроцессоров: `heading_normalizer → unnumbered_heading_detector →
listing_wrapper → html_table_converter → caption_folder → inline_normalizer`.

## 2. Преобразования постпроцессора

### 2.1 Заголовки

| Pandoc вывод | Наш MD | Комментарий |
|---|---|---|
| `# 1 Введение` | `# Введение` | срезаем ведущую нумерацию `\d+(\.\d+)*\s+` |
| `## 1.2 Метод` | `## Метод` | то же |
| `# СОДЕРЖАНИЕ` | `# СОДЕРЖАНИЕ {.unnumbered}` | эвристика для H1 |

Ненумерованными становятся H1 с текстом (case-insensitive) из набора
{СОДЕРЖАНИЕ, ВВЕДЕНИЕ, ЗАКЛЮЧЕНИЕ, СПИСОК ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ}.
Ручную нумерацию срезаем всегда — экспорт нумерует сам, иначе получим
двойную при ре-экспорте.

### 2.2 Подписи блоков

Подпись в Word — отдельный параграф до или после блока; pandoc отдаёт её как
обычный текст. Регулярка (case-insensitive):

```
^(Таблица|Рисунок|Рис\.?|Листинг)\s+\d+(\.\d+)*\s*[—\-.:]\s*(.+)$
```

Свёртка (не дальше двух пустых строк от блока):

| Pandoc вывод | Наш MD |
|---|---|
| `Таблица 1 — Продукты` + GFM-таблица | таблица + `: Продукты` **после** неё |
| `Листинг 1 — Merge sort` + code-block | fence + `: Merge sort` после |
| `Рисунок 1 — Схема` + `![](img.png)` | `![Схема](img.png)` (подпись → alt) |

Номер выбрасывается (экспорт генерирует сам), исходная строка с подписью
удаляется. Атрибуты в подпись не восстанавливаются — только текст.

### 2.3 Listing detection (моноширинный шрифт)

Pandoc не превращает моноширинные параграфы в code-blockи. Эвристика:

1. До pandoc (по `python-docx`) собираем группы подряд идущих параграфов, у
   которых каждый непустой run имеет шрифт из {Courier New, Consolas, Monaco,
   Menlo, Source Code Pro, Liberation Mono, DejaVu Sans Mono}.
2. После pandoc сопоставляем группы по первой/последней строке текста и
   оборачиваем в `` ``` ``-блок (без языка).
3. Подпись «Листинг N — …» докручивается дальше правилом §2.2.

Если сопоставить не удалось — не оборачиваем, fallback `stage=listing`,
блок остаётся текстом. Не падаем.

### 2.4 Inline-форматирование

| Pandoc вывод | Наш MD |
|---|---|
| `**bold**`, `*italic*`, `~~strike~~`, `` `code` `` | без изменений |
| `[text]{.underline}` | `[text]{.underline}` (каноническая форма, переизлучается) |
| `[text]{.smallcaps}`, `[text]{.mark}`, прочие spans | обычный `text` (атрибут отбрасывается) |

### 2.5 Списки

`1.`/`-` остаются как есть. Иерархическая нумерация применяется экспортом.

### 2.6 Таблицы

GFM `pipe_tables` не трогаются; свёртка подписи — §2.2. `widths`/`heights`
импорт не восстанавливает (нет надёжного источника в docx) — все таблицы
autofit.

#### 2.6.1 Raw HTML `<table>`

При `colspan`/`rowspan`, multi-paragraph ячейках, картинках или явных
ширинах pandoc сваливается в raw HTML. Трансформер `html_table_converter`
конвертирует его в pipe-table:

- колонок = максимум суммы `colspan` по строке;
- `<thead>` → header, иначе первая строка промотится + синтетический `---`;
- `colspan="N"` → ячейка + N−1 пустых справа; `rowspan="N"` → по одной пустой
  в N−1 строках ниже (текст не дублируется) — стратегия flatten;
- multi-paragraph ячейка / `<br>` → `A / B`;
- `strong/b`→`**`, `em/i`→`*`, `u`→`[…]{.underline}`, `code`→`` ` ``,
  `img`→`![alt](src)`;
- вложенная `<table>` остаётся raw-HTML, fallback `stage=html_table`.

Flatten, а не визуальный merge, выбран сознательно: pipe-tables не
выражают span'ы, импорт lossy by design. Для титульников с merge
правильнее шаблоны `::: {.template name="titlepage-…"}`, а не импорт
чужого docx.

### 2.7 Формулы

OMML → LaTeX автоматически; `$…$`/`$$…$$` без изменений (см. также
prepass-разворот «математических» таблиц в §1). Формула-картинка (OLE)
остаётся картинкой — документированное ограничение.

### 2.8 Картинки

Каждая картинка получает имя = первые 32 hex-символа sha256 содержимого,
без расширения — дедупликация по контенту бесплатна.

| Режим | Ссылка в md | Байты |
|---|---|---|
| CLI (`images_dir`) | `<имя_каталога>/<id>` | файл в `images_dir` |
| API (`images_prefix`) | `<prefix>/<id>` | `Storage.put(<prefix>/<id>)` |

Битая ссылка (pandoc сослался на несуществующий файл в media/)
заменяется на детерминированный плейсхолдер `![](missing/{N})` и
инкрементит `md2gost_import_fallback_total{stage=image}`.

### 2.9 Разрывы страниц

`<w:br w:type="page"/>` не распознаётся и не восстанавливается — экспорт
делает разрывы по геометрии страницы.

## 3. Что НЕ распознаётся

- Шаблоны (`::: {.template …}`) — слишком высокий риск ложных срабатываний
- Mermaid-диаграммы (в docx — обычные картинки)
- Сноски (Word footnotes)
- Колонтитулы, поля, закладки, комментарии, track changes (pandoc сжимает
  в accepted-вариант)

## 4. Поведение при ошибках

Исключение в шаге постпроцессора локализуется и логируется; блок остаётся
в raw-виде от pandoc; `md2gost_import_fallback_total{stage}` растёт
(stages: `heading`, `image`, `listing`, `html_table`, `pdf_prepass`);
импорт не прерывается. Полный fail — только ошибка pandoc/unoserver на
верхнем уровне (битый файл, таймаут).

## 5. PDF через unoserver-prepass

1. `pdf_to_docx(pdf_path)` — XML-RPC к unoserver (фильтр
   `writer_pdf_import`), DOCX во временный файл.
2. Дальше обычный `import_docx`; tmp-DOCX удаляется.

`import_file` диспетчеризует по расширению (`.docx`/`.pdf`, регистр
игнорируется); прочие расширения — `ValueError`.

### Восстановление textbox (пустой prepass)

Если markdown после prepass пуст/почти пуст, из DOCX XML повторно
собираются тексты листовых параграфов и синтезируются `# первая строка` +
абзацы — частичный salvage для «плохих» конвертаций.

### Ограничения

- **OCR нет.** Скан без текстового слоя даёт пустой DOCX; импорт не падает,
  fallback `stage=pdf_prepass`. Решение — внешний OCR до подачи.
- **Формулы → картинки** (векторные рисунки в PDF LibreOffice вкомпилит как
  изображения).
- **Сложные многоколоночные/табличные вёрстки** конвертируются хуже
  линейных — ограничение LibreOffice.
- **Шрифты** без mapping-таблицы могут дать «крякозябры».

### Таймауты и метрики

- `PDF_PREPASS_TIMEOUT_SECONDS` (60 c, отдельный от `PANDOC_TIMEOUT_SECONDS`).
- `md2gost_import_duration_seconds{format}`, `md2gost_import_total{format,result}`,
  `md2gost_import_fallback_total{stage}`.
