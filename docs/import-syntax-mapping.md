# Import: маппинг DOCX/PDF → md2gost MD

Нормативный контракт результата: [skills/markdown-gost/syntax.md](../skills/markdown-gost/syntax.md).
Импорт выдаёт только новый синтаксис, без legacy-режима.

Документ описывает, что именно постпроцессор распознаёт в выводе pandoc и во что
сворачивает. Всё, что не описано здесь, оставляется «как есть» из pandoc.

PDF-вход (T041) проходит через unoserver-prepass: PDF → DOCX → дальше всё то же.
См. [§5 ниже](#5-pdf-через-unoserver-prepass) про специфику и ограничения.

См. [ADR-0006](adr/0006-import-pipeline.md) для общей стратегии.

## 1. Pandoc-вызов

Перед вызовом создаётся временная семантическая копия DOCX, если обнаружены
структуры md2gost: стиль `MD2GOST Structural Heading` становится распознаваемым
заголовком первого уровня, а невидимые таблицы «формула — номер» разворачиваются
в display math. Это сохраняет структурные заголовки и простые/сложные формулы
при roundtrip. Оригинал DOCX не изменяется, обычные таблицы не разворачиваются.

```
pandoc input.docx \
  --from=docx \
  --to=markdown_strict+pipe_tables+backtick_code_blocks+tex_math_dollars+raw_tex+bracketed_spans \
  --extract-media=<tmpdir>/media \
  --wrap=none \
  -o raw.md
```

- `markdown_strict` как база — меньше pandoc-специфичных конструкций
- `pipe_tables` — GFM-таблицы (постпроцессор ожидает их)
- `tex_math_dollars` — формулы в `$...$` / `$$...$$`
- `bracketed_spans` — pandoc-spans вида `[text]{.underline}`
- `--wrap=none` — никаких авто-переносов, чтобы regex-обработка была надёжной
- `--extract-media` — все картинки в temp-папку, ссылки в md переписываются на
  пути относительно temp-папки

## 2. Преобразования постпроцессора

### 2.1 Заголовки

| Pandoc вывод | Наш MD | Комментарий |
|---|---|---|
| `# 1 Введение` | `# Введение` | срезаем ведущую нумерацию `\d+(\.\d+)*\s+` |
| `## 1.2 Метод` | `## Метод` | то же |
| Заголовок с неизвестным названием | Обычный Markdown-заголовок | отсутствие номера в DOCX само по себе не позволяет надёжно восстановить роль |
| `# СОДЕРЖАНИЕ` | `# СОДЕРЖАНИЕ {.unnumbered}` | эвристика для известных служебных названий верхнего уровня |

Логика: наш экспорт сам нумерует, поэтому возвращать ручную нумерацию вредно —
получим двойную при ре-экспорте.

### 2.2 Подписи блоков

В Word подпись обычно идёт **отдельным параграфом** до или после блока. Pandoc
отдаёт её как обычный текст. Постпроцессор сворачивает.

| Pandoc вывод (до блока) | Наш MD |
|---|---|
| `Таблица 1 — Продукты` + GFM-таблица | Та же таблица, затем `: Продукты` |
| `Таблица 1. Продукты` + GFM-таблица | Та же таблица, затем `: Продукты` |
| `Рисунок 1 — Подпись` + `![](img.png)` (на след. строке) | `![Подпись](img.png)` |
| `Рис. 1. Подпись` + картинка | `![Подпись](img.png)` |
| `Листинг 1 — Merge sort` + fenced code | Тот же блок, затем `: Merge sort` |

Регулярка для заголовка подписи (case-insensitive):
```
^(Таблица|Рисунок|Рис\.?|Листинг)\s+\d+(\.\d+)*\s*[—\-.:]\s*(.+)$
```

Подпись может идти **до** или **после** блока — постпроцессор смотрит соседние
строки в обоих направлениях. Удаляем оригинальную строку с подписью.

Номера подписей **выкидываются** — наш рендер их генерирует сам.

### 2.3 Listing detection (моноширинный шрифт)

Pandoc по умолчанию **не** превращает моноширинные параграфы в code-blocks —
отдаёт как обычный текст в `code-spans`. Эвристика:

1. На уровне docx-парсинга (через `python-docx`, до pandoc) собираем set
   параграфов, у которых **все runs** имеют `font.name ∈ {Courier New, Consolas,
   Monaco, Menlo, Source Code Pro, Liberation Mono}`.
2. Для каждой группы подряд идущих таких параграфов запоминаем «позицию» —
   индекс параграфа в документе.
3. После pandoc сопоставляем индексы и оборачиваем соответствующие строки в
   ` ```...``` ` блок.
4. Если рядом есть «Листинг N — Caption» — добавляем `: Caption` после блока.

При невозможности сопоставить (нумерация съехала, pandoc объединил параграфы) —
просто не оборачиваем. Fallback — обычный текст. Не падаем.

### 2.4 Inline-форматирование

| Pandoc вывод | Наш MD |
|---|---|
| `**bold**` | `**bold**` |
| `*italic*` | `*italic*` |
| `~~strike~~` | `~~strike~~` |
| `[text]{.underline}` | `[text]{.underline}` |
| `` `code` `` | `` `code` `` |
| `[text]{.smallcaps}`, `[text]{.mark}` и т.д. | обычный `text` (атрибут отбрасываем) |

### 2.5 Списки

Pandoc корректно отдаёт `1.`/`-` списки. Постпроцессор оставляет как есть.
Иерархическая нумерация наша (T011a) применится сама при ре-экспорте.

### 2.6 Таблицы

GFM `pipe_tables` от pandoc остаются нетронутыми. Свёртка caption → `: Подпись`
описана в 2.2. Параметры `widths=...`/`heights=...` импорт **не восстанавливает**
(нет надёжного источника в docx) — все таблицы становятся autofit.

#### 2.6.1 Raw HTML `<table>` (T046)

Если в docx таблица содержит `colspan`/`rowspan`, multi-paragraph ячейки,
картинки или явные ширины колонок, pandoc не может выразить её как
`pipe_tables` и сваливается в raw HTML (`<table>…</table>`). Постпроцессор
ловит такие блоки и конвертирует их в pipe-table (трансформер
`html_table_converter`, см. `postprocessor/README.md`). Правила:

- Число колонок = максимум суммы `colspan` по строке;
- `<thead>` → header row; иначе первая строка промотится в header
  и под ней рисуется синтетический separator `|---|---|…`;
- `colspan="N"` → исходная ячейка + `N-1` пустых ячеек справа;
- `rowspan="N"` → исходная ячейка + по одной пустой ячейке в `N-1`
  строках ниже на том же индексе (текст **не** дублируется);
- Multi-paragraph ячейка (`<td><p>A</p><p>B</p></td>`) → `A / B`
  внутри pipe-cell. Использовать `<br>` нельзя: рендер md2gost
  складывает `LineBreak` в пробел в пределах параграфа (см. T046a);
- `<strong>`/`<em>`/`<u>`/`<code>` → `**`/`*`/`[текст]{.underline}`/`` ` ``;
- `<img src=… alt=…>` → `![alt](src)` (атрибуты ширины/высоты не
  переносятся, как и в §2.8 для обычных картинок);
- Вложенная таблица (`<table>` внутри `<td>`) — pipe-tables её
  выразить не могут, блок остаётся в raw-виде, метрика
  `md2gost_import_fallback_total{stage=html_table}` инкрементится.

Стратегия **flatten** (а не визуальный merge ячеек DOCX) выбрана
сознательно: рендер md2gost-таблиц поверх `pipe_tables` не
поддерживает span'ы, а импорт по определению lossy (ADR-0006). Для
титульных листов с реальным merge корректнее использовать шаблоны
`.template name="titlepage-university"`, а не импортировать раскладку из чужого docx.

### 2.7 Формулы

Pandoc конвертирует OMML → LaTeX автоматически. Инлайн `$...$`, блочные `$$...$$`
остаются как есть.

Если в исходнике формула была картинкой (OLE-объект или image) — pandoc отдаст
картинку, формулой её обратно не сделать. Это документированное ограничение.

### 2.8 Картинки

| Источник | Результат |
|---|---|
| `![](media/image1.png)` от pandoc | `![](<images_dir_name>/img-1.png)` (CLI) или `![](<images_prefix>/img-1.png)` (API) |
| `<img src="media/image1.png" width="…"/>` (raw HTML, pandoc fallback при наличии атрибутов в `markdown_strict`) | `![](<images_dir_name>/img-1.png)` — атрибуты ширины/высоты не сохраняются |

Имена файлов нормализуются в `img-<N>.<ext>` в порядке встречи в документе.
Сами байты заливаются либо в локальную `images_dir` (CLI), либо через
`Storage.put` под `images_prefix` (API). Битые ссылки (pandoc сослался на файл,
которого нет в media/) увеличивают `md2gost_import_fallback_total{stage=image}`;
исходная ссылка остаётся как есть.

### 2.9 Разрывы страниц

В docx разрыв страницы — это `<w:br w:type="page"/>`. Pandoc по умолчанию
**не** отдаёт его в markdown. Постпроцессор не пытается восстановить — наш
рендер делает разрывы автоматически по геометрии страницы.

## 3. Что НЕ распознаётся

- Шаблоны (`.template`) — слишком высокий риск ложно-положительных
- Mermaid-диаграммы (в docx они — обычные картинки)
- Сноски (Word footnotes) — наш экспорт их не поддерживает, pandoc выкинет
- Колонтитулы, поля, закладки
- Комментарии (Word review comments) — игнорируем
- Track changes — pandoc сжимает в accepted-вариант

## 4. Поведение при ошибках

- Любая `Exception` в шаге постпроцессора локализуется и логируется
- Блок, на котором упали, остаётся в raw-виде от pandoc
- Счётчик `md2gost_import_fallback_total{stage}` инкрементится
- Импорт **не прерывается** на одном проблемном блоке

Полный fail возможен только если pandoc/unoserver вернули ошибку на верхнем
уровне (битый файл, таймаут).

## 5. PDF через unoserver-prepass

PDF-импорт реализован как двушаговый пайплайн (T041, ADR-0006):

1. `pdf_to_docx(pdf_path)` — XML-RPC вызов к unoserver, LibreOffice рендерит
   PDF в DOCX во временный файл.
2. Результат передаётся в обычный `import_docx`; tmp-DOCX удаляется после.

Дисптчер `import_file(path, ctx)` выбирает между `import_docx` и `import_pdf`
по расширению (`.docx` / `.pdf`); регистр игнорируется.

### Ограничения

- **OCR нет.** Сканированные PDF (без текстового слоя) дают пустой или
  почти пустой DOCX. Импорт **не падает** — возвращает то, что вернул
  LibreOffice, и инкрементит `md2gost_import_fallback_total{stage=pdf_prepass}`.
  Решение пользователю: прогнать PDF через внешний OCR (tesseract и т.п.)
  и подать результат заново.
- **Формулы → картинки.** В PDF формулы — векторные рисунки. LibreOffice
  чаще всего вкомпилит их как изображения в DOCX; постпроцессор их
  пропустит как обычные `![](...)`, а не как `$...$`/`$$...$$`.
- **Сложные многоколоночные / табличные верстки** конвертируются хуже, чем
  «линейные» одноколоночные PDF. Это ограничение LibreOffice, не наше.
- **Шрифты.** Если PDF использует embedded font без mapping-таблицы, текст
  может прийти как «крякозябры». Лечится только пересборкой исходника.

### Таймаут

`PDF_PREPASS_TIMEOUT_SECONDS` (env, по умолчанию 60). Отдельный от
`PANDOC_TIMEOUT_SECONDS`, потому что большие PDF могут конвертироваться
дольше, чем самый медленный docx-pandoc-проход.

### Метрики

- `md2gost_import_duration_seconds{format="pdf"}` — общее время prepass + docx-импорта.
- `md2gost_import_total{format="pdf",result="success|error|fallback"}` — счётчик
  результатов (success всегда; fallback добавляется если был ≥1 fallback-стейдж).
- `md2gost_import_fallback_total{stage="pdf_prepass"}` — пустой/почти пустой
  DOCX после конвертации (диагностический сигнал «возможно, скан без OCR»).
