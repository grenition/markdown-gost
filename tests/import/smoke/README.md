# Import smoke tests (T040)

Запускают импорт-пайплайн на **реальных «грязных» docx** из архивов МИРЭА
(дипломы, курсовые, отчёты) и проверяют, что пайплайн:

1. **не падает** (не бросает исключений);
2. выдаёт **разумный объём** markdown (`min_chars`);
3. укладывается в лимит fallback-ов (`max_fallbacks`);
4. содержит ожидаемые подстроки (`must_contain`);
5. имеет минимум структурных блоков (`must_have_at_least`).

Не сравнивают вывод с эталоном — для этого есть golden-тесты (T038) и
roundtrip-тесты (T039). Smoke — это последняя линия обороны от паник.

## Запуск

```bash
make test-import-smoke
```

Если фикстуры (`input.docx`) отсутствуют локально, соответствующий кейс
**skip**-ается — CI без приватного архива всё равно проходит.

## Политика хранения фикстур

Файлы `input.docx` **не коммитятся в git** напрямую. Причины:

- Реальные документы содержат ФИО, ссылки, иногда персданные.
- Размер: типовая работа 5–30 MB; 5 кейсов = 100+ MB шума в репо.
- LFS — лишний инструмент в проекте, который и без того тяжёлый по
  зависимостям; для smoke-тестов выгоды нет.

Поэтому `**/input.docx` стоит в `.gitignore` этой директории. Файлы
хранятся локально у разработчика (и/или в приватном бакете команды; путь
к нему фиксируется в локальной `.env`, не в репо).

Если **обязательно** надо завести общий пул фикстур — миграция на git-lfs
делается без поломки тестов: достаточно убрать строку из `.gitignore` и
прогнать `git lfs track "**/input.docx"`.

## Как добавить новый кейс

1. Создать директорию `tests/import/smoke/NN-name/` (две цифры с
   ведущим нулём для сортировки).
2. Положить туда `input.docx` — это **локальный** файл, в git не
   попадёт.
3. **Обезличить** docx, если содержит ФИО/контакты других людей
   (заменить на «Иванов И. И.», убрать e-mail / телефоны).
4. Создать `expectations.yaml` — формат ниже.
5. Запустить `make test-import-smoke`, убедиться, что кейс проходит.
6. Закоммитить только `expectations.yaml` (docx останется
   gitignore-нутым).

## Формат `expectations.yaml`

```yaml
min_chars: 5000           # минимальный объём итогового markdown в символах
max_fallbacks: 25         # суммарный потолок fallback-ов (по всем стадиям)
must_contain:             # подстроки, которые ОБЯЗАНЫ присутствовать
  - "Введение"
  - "Заключение"
must_have_at_least:       # минимальные счётчики структурных блоков
  headings: 5             #   доступные ключи: headings, tables,
  tables: 1               #   images, equations, listings
```

Все поля опциональны (пустые/нулевые значения = «не проверяем»). Списки
по умолчанию пустые.

### Подбор порогов

- `min_chars` — открыть исходный docx, посмотреть на объём текста,
  взять **70–80%** от него (импорт всегда теряет часть форматирования).
- `max_fallbacks` — запустить кейс впервые с `max_fallbacks: 1000`,
  посмотреть фактический `fallback_total`, взять **+20%** запаса.
- `must_contain` — выбрать слова, которые точно есть в работе и
  пишутся без вариаций орфографии («Введение», «Список литературы»).
- `must_have_at_least` — **нижние** границы, не точные значения.
  Цель — поймать ситуацию «у нас вдруг 0 заголовков», а не
  «было 12, стало 11».

## Минимальный размер пула

Целевое: **3–5 кейсов**. Меньше — нерепрезентативно; больше — долгий
прогон без выигрыша.

## Smoke fails — что делать

Кейс упал → **не блокирует** релиз и не блокирует автоматизированную
отладку (smoke сам по себе regression-тест, как T039 roundtrip).
Регламент:

1. Открыть stderr теста, посмотреть на конкретное assertion.
2. Если просел один счётчик в `must_have_at_least` — выяснить, что
   изменилось в постпроцессоре/детекторе и почему.
3. Если `fallback_total` пробил потолок — посмотреть `result.fallbacks`
   в выводе теста, понять, какая стадия деградировала.
4. Решение «починить пайплайн» vs «ослабить порог» — на усмотрение
   ответственного. Ослаблять пороги без причины запрещено.
